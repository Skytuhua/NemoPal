# Local NemoPal demo: integration status

This checkout contains the desktop Codex demo, Sendblue transport, phone enrollment, and pet drag/chat code. It is **not yet a single Codex-and-texting demo**. The workspace Codex demo starts a separate in-memory local thread; pet chat and Sendblue use the cloud manager and its Nemotron adapter. No code connects Sendblue messages or pet chat to that Codex thread.

## Prepare offline

With Node 24.14.x and pnpm 10.30.3, from this checkout run `pnpm install --offline --frozen-lockfile --ignore-scripts`, then `pnpm typecheck` and `pnpm build`. These do not start the app. The build may report a large web bundle warning.

## Before any live demo

1. Resolve the previously rejected local-backend startup through its owning authorization process. Do not retry it or expose the laptop to obtain a webhook. An approved, owned API/database and normal desktop pairing are prerequisites; [setup.md](setup.md) describes the existing setup but is not permission to start it.
2. Complete and verify a bounded Codex manager integration if Codex is intended to answer pet and text messages. The existing [Codex demo](codex-local-demo.md) is a separate conversation; its local folder disclosure and provider usage still apply. No T3 connection is included.
3. For local polling, set `NEMOPAL_SENDBLUE_ENABLED=true` and `NEMOPAL_SENDBLUE_POLL_ENABLED=true` in the cloud process, along with the Sendblue configuration names in [Sendblue integration](evidence/sendblue-integration.md). Keep values private. The existing configuration still requires a separate webhook secret even when no webhook is configured. Run the existing explicit migration against the authorized database before starting the cloud process (`pnpm db:migrate`, then `pnpm dev:cloud`); retain its loopback `PUBLIC_ORIGIN` and all existing database, owner-authentication and model prerequisites. This does not resolve the previously blocked local backend startup. In the paired desktop, select the project, open Project settings → Phone messaging, enter your own number in international format, explicitly consent, and select Link phone. Links created before this migration must be re-linked to receive by polling. The grant lasts six days; use Revoke phone access to withdraw it. No public webhook, listener or tunnel is needed for the poller. Automatic notification producers are not connected to the notification queue.

   Polling is offline-tested only. Each tick scans the linked sender's post-consent history twice, requires matching complete pagination, and sends STOP to canonical acceptance before ordinary messages. An ambiguous response, missing timestamp, changed page, or more than 1,000 matching messages stops that tick and holds its delivery; the next tick rescans from consent and existing receipts deduplicate. Run only one local cloud process: another process without polling can still deliver. Provider timestamps, complete list visibility and stable pagination are not guaranteed by these local checks: delayed or omitted messages, including STOP, may be invisible after a successful scan. A local demo requires separate validation of the provider contract, clock alignment, database migration and the existing startup/model gates; this is not a live acceptance claim.
4. After the applicable gates and explicit live-test authorization, verify desktop pairing, pet chat, Codex, and a two-way text using a known authorized contact. Check actual delivery and retain only redacted results. Do not send another text as part of offline preparation.

This is a handoff for the remaining work, not a claim of native, live, or user acceptance.
