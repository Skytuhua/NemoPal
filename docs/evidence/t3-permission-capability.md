# T3 questions, permissions, and notification capability

Research-only handoff, 2026-11-08. NemoPlaybook base and initial clean HEAD: `6f43f2bc728bfb7193d1c7c44ab979a1865e048e`. Ownership: this new evidence file only. No T3 thread or service was called, no private source read or exported, no native GUI, message, SMS, provider, or deployment used. This is static evidence, not a live integration or acceptance result.

## Finding

The inspected T3 MCP interface **does not provide a supported permission-approval response**. `t3_pending_request` answers pending **user-input questions**, not tool, filesystem, command, or privilege approvals. A human can be notified that attention is needed and return to T3's own approval surface; the product must not say that the pet or an SMS reply approved anything. The prior automatic-policy rejection remains a rejection, not an unanswered approval to retry or bypass.

This conclusion is scoped to the exact installed artifact and exposed tool catalog inspected here, not all possible T3 versions or undocumented interfaces. An internal command or third-party bridge is not evidence of an authorized public approval API.

## Routes and gaps

| Need | Supported evidence | Gap and safe behavior |
| --- | --- | --- |
| Detect a T3 question | `t3_pending_request` list/read, scoped to an explicitly authorized thread; delegated work can signal a pending question. | No T3 call is authorized or exercised by this investigation. Current observer is read-only; a new connector needs explicit consent, scope and capability checks. |
| Return a human answer to a question | `respond` accepts `requestId` and `answers` after checking the matching request remains pending. | Existing pet answers have a different schema and destination. Preserve exact question IDs, options, required/multiselect/custom-answer semantics and user intent; do not map a generic Recorded button to a T3 answer. Dispatch acceptance is not proof of provider completion. |
| Notice an approval | Delegated `pendingApproval` is a signal; thread `activity` can contain an approval item. | Counts or empty question lists do not establish type, identity, current validity, or delivery. Stale projections and provider callbacks are possible. Tell the user to inspect the original T3 surface; do not display an actionable Approve control without a supported authority channel. |
| Return an approval | No supported MCP approval response in the inspected interface. | Human decides in T3's own surface when available. A chat message, ordinary question response, mode change, implicit consent, private endpoint, or automatic retry is not a substitute. This does not reverse a policy rejection. |
| Pet notice | Existing pet presents Playbooks check-ins under its existing policy. | A separate typed attention notice and open-in-T3 navigation need an authorized source, a safe local route, identity and stale fences. Generic notice should avoid copying commands or private text without separate permission. No claim of native visual delivery. |
| Text/SMS notice and reply | No SMS implementation was found in the scoped app/package search; design explicitly disables it. | Needs an opted-in channel/provider, verified destination, cost/credentials, delivery/replay and inbound authentication, privacy, consent and revocation. SMS can carry a generic notice and return user to T3; replying cannot approve a permission via the inspected API. No real text or provider use was performed. |

## Smallest next implementation steps

1. As a disjoint synthetic-only leaf, specify a pure attention classifier/presentation model with explicit `question`, `approval_attention`, and `unknown` variants. It accepts already-authorized fixture projections and produces generic notice plus an opaque local navigation intent; it has no T3 client, network, source text, SMS, credential, or permission mutation. Test stale/resolved/replaced request, duplicate delivery, scope/owner switch, unknown kinds, truncated details, and no approval action. Do not modify shared schemas or wire it into the pet without the owning lane's contract agreement.
2. Separately design a question adapter with explicit user opt-in and least-privilege thread binding. Read the current request immediately before presenting and again before responding; bind environment, thread, request and question identities, preserve typed answers, handle stale/duplicate/ambiguous responses, and report a receipt only as the returned result establishes. Include consent revocation and no automatic interpretation of free text as authority. This is a new write capability, separate from the current observer.
3. For permission requests keep a generic attention indicator and user-directed return to the native T3 approval UI. Require a documented supported T3 approval API, explicit security design and user authorization before any remote approval implementation. Design SMS only as a separately authorized channel with authenticated replies and durable reconciliation; until then it remains disabled.

No source code, tests, provider calls, live T3 state, UI behavior, or delivery was changed or verified by this report. A future supported question reply is not equivalent to a permission grant. Real integration, native pet behavior, SMS delivery, privacy review and user acceptance remain open.
