## Delivered interfaces

All exports are additive from `apps/cloud/src/integrations/t3/index.ts`. Importing them starts no timers, sockets, MCP session, provider, or poller.

- `connectionPreview(endpoint)` validates an explicit HTTPS or loopback-HTTP `/mcp` address without embedded credentials/query/hash. It returns the fixed tool list, permission requirements, OAuth requirement, `not_tested` connection state and `writesConfiguration: false`. It never installs MCP or changes a profile.
- `T3McpClient` is the real-transport adapter boundary: a parent-supplied dedicated OAuth MCP client with selected endpoint/environment metadata, negotiated tool names, authenticated permissions, and `callTool(name,args,signal)`. Implement the SDK bridge against the actual reviewed endpoint. There is no built-in OAuth login/credential store or HTTP wire client, and no installed MCP SDK dependency in this leaf. Actual client creation and sign-in remain **unimplemented parent integration**, not a fabricated connected state. The client must remain bound to that endpoint, honor cancellation, enforce response-size limits before parsing and avoid logging headers/raw bodies.
- `T3Adapter` permits only `t3_thread_read` and `t3_pending_request` with explicit selected environment/thread arguments. Unknown capabilities stay off, grants/mappings are checked before and after awaits, and each call has a five-second deadline. A late result cannot publish after cancellation. Reads use 25 items, 10 recent runs and **one character per item**, the public tool's minimum. Title/text/type and unrecognized fields are discarded. Inherited/synthetic/other-source items are discarded, and their links are never followed. This is no transcript export; the server can still return a one-character preview and inherited metadata because the public read API lacks a zero-content/local-only option. For a strict zero-content wire guarantee, T3 needs a metadata-only, local-only read option; do not enable observation under such a policy before that exists.
- `T3Observer(context,adapter,now,checkpoint?)` provides bounded `poll`, `snapshot` and `cancel`. Poll no faster than once per second; at most two read calls per tick, 100 retained metadata items, stale after 15 seconds. Reconnect restores only matching scoped metadata/cursor and requires fresh reads. New runs are `unmapped` until the parent explicitly revises the mapping. Plain labels and item statuses support accessible board rendering; there is no progress percentage. Parent owns reduced-motion/native display.
- `completionProposal(context,observation,receipt,verifyReceipt,authority,now,signal?)` returns a proposal or `null`. It requires an enabled current owner policy, matching fresh completed thread **and selected run**, exact task/mapping/run/grant/policy revisions, and a trusted correlated success receipt verifier. Prose, failed/stopped/interrupted runs, and thread completion alone do nothing. It performs no canonical task mutation. There is no public T3 business-task-success oracle or receipt verifier implemented here.
- `T3Attention` uses an injected canonical `AttentionRepository`, two `NotificationSink` ports and an optional trusted `QuestionRunBindingPort`. `captureQuestion(requestId)` brackets pending-request list/read with current-run reads, pins the full identity/definition digest and stores a five-minute challenge capped by grant/proof expiry. Re-observation does not extend expiry. Only current running/waiting mapped runs are supported; questions left on an older/post-turn run require manual T3 handling. Without independent run evidence, the record says `observed_current_run` and remote response stays **manual**. A valid matching proof changes that to `verified_request_run`; its source is a required parent extension, not a capability the current public tool offers.
- `notify(requestKey)` queues generic pet and Sendblue notices independently. No question/option body, transcript, action secret, model output or real answer is sent to either sink. The opaque response code is correlation data, not owner authentication. A failed enqueue reuses the same per-sink operation ID; a successful sink is preserved. A read-only question gets a truthful manual fallback. No provider messages are sent by this leaf.
- `respond(principal,envelope)` requires the parent's authenticated owner/channel identity, matching device/source binding, request/run/grant/digest/challenge and offered-answer validation. It rechecks the live question, run proof and authority. One atomic CAS reserves the response; operation and answer digests prevent replay/concurrent retransmission. No raw answer is stored in this leaf. The canonical ingress must retain the real human response if retrying a pre-send attempt. The text-only subset rejects unknown questions/unsupported answer shapes and defaults custom answers off unless expressly offered. A missing, changed, expired or wrong-run proof prevents remote return; tool names/scopes alone cannot enable it.
- Response stages are `received` (reserved for the exact operation), `sending`, `accepted` (T3 dispatch sequence), and `uncertain`. A crash/lost acknowledgement in `sending` never triggers automatic resend. `reconcile` can mark the request `not_pending`, which does **not** prove this answer reached the provider or succeeded. Provider delivery and actual request resolution need separate later evidence.
- `permissionNotice` accepts only an already scoped parent notice and retains offered decisions/digest/expiry. The public pending tool cannot discover permissions; this leaf does not pretend it can. All permission responses are hard-disabled; `answerPermission` always rejects, including with a permissive mock. Both notification paths say **Open in T3** and manual resolution. A question is never converted into an approval or ordinary chat command.

## Remaining T3 extension and actual acceptance gates

OAuth connection is publicly supported; its real client, credential lifecycle and reachability are **untested/unwired** here. Permission discovery/return remains **unsupported** by the public question tool. Minimal required T3 extension: a documented authenticated scoped request API exposing exact environment/project/thread/run/request identity, request revision, action digest, offered decisions, expiry and callback liveness; a narrowly authorized response with atomic pending/run/digest/revision comparison and idempotency; distinct accepted/provider-delivered/resolved results; normal T3 policy and revocation enforcement. Saved request records and internal dispatch schemas are insufficient. Never retry or reroute policy-blocked J2 through this or any synthetic notice.

The existing public question API omits request/run association and has an observation/response race: it does not accept an expected run or definition digest. Consequently the default workflow is question notification + manual Open in T3. Injected tests exercise the future correlated response path with independent proof fixtures; they do not promote the current public protocol to support atomic run correlation or native provider delivery. The scoped request-identity/compare-and-respond extension is a release gate for that stronger path. The module revalidates before sending and addresses the exact request ID, while the public handler checks pending question kind/status; this still does not make a later unacknowledged provider result successful.
