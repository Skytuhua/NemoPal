# Local T3 application session: implementation boundary

This leaf starts at the exact PR #47 head `f919055f6e24146c48262c7bd8bdd5eab7dfd451`, which includes PR #46. The supplied worktree was clean at `6f43f2bc728bfb7193d1c7c44ab979a1865e048e` before the branch was created. No live T3 authorization or connection was attempted.

`openLocalT3Session` reuses the dedicated local OAuth and official MCP SDK connector. It retains the read-only bearer in process memory and returns a `T3McpClient` for `T3Adapter`; it does not register a route, scheduler, renderer or service. It binds one environment and thread, restricts calls at both client and fetch boundaries to bounded activity reads and pending-question list/read, and permits no question response or permission operation. Each request has a maximum five-second deadline, only one can be active, and a session is limited to 300 calls and five minutes or the token lifetime, whichever is shorter. There is no automatic refresh, replay, or reconnect.

The session is closed on expiry, owner-supplied cancellation, or explicit close. Close during an active call aborts it and performs no new remote termination request. If an established remote session cannot be confirmed terminated, `close` reports uncertain cleanup; local access remains closed. The T3 approval itself is separate and may require the owner to revoke it in T3. The bearer is not passed to a model, renderer or generic proxy. JavaScript cannot guarantee memory zeroization.

The existing adapter still performs grant and mapping checks before and after a call; its observer strips private fields and inherited items from the retained projection. Server responses can still contain a one-character preview and inherited metadata on the wire. An integrator must not expose the raw client or call it outside the adapter: the parent must provide canonical authority, close on grant withdrawal and shutdown, and protect the local process. Client selection is a local restriction, not a narrowly scoped server-side OAuth grant.

The existing workflow is exercised through the real SDK and OAuth code against a synthetic server, including observer projection, a revoked authority, scoped arguments and cleanup. This is not a production app registration or live acceptance. The production joins remain canonical enrollment/authority, trusted task and run mapping, scheduler/checkpoint lifecycle, authenticated review and owned UI, durable attention/outbox ports, and revocation integration. Remote question response remains disabled without the independently trusted run binding and compare/respond support described in PR #46; native permission response remains unsupported. Completion still requires a trusted receipt and canonical task commit. Native, model, database, provider and deployment paths were not exercised.
